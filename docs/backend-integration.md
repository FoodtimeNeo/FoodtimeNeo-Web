# Web 真实后端接入

本轮只修改 Web。接口以现有 Backend 的 `docs/api` 和 `docs/database-design.md` 为依据，不补造后端字段或接口。按用户确认隐藏邀请码、吐槽、推荐/避雷、今日推荐及排行榜等未支持入口；不新增点赞、收藏或分类。正式邮箱投递仍暂不验证。

## 认证与请求

- 本地开发使用 `/api/v1` 同站请求，Vite 将 `/api` 代理至 `http://127.0.0.1:8080`。生产需将同站 `/api/v1` 代理至 Backend，并使用 HTTPS；不能把开发服务器当作生产部署。
- Web 浏览器地址使用 `http://localhost:5173`，或空闲的 `http://localhost:3000`。当前 Backend 开发白名单只接受这两个来源，浏览器使用 `127.0.0.1:5173` 会被拒绝。开发代理仅接受本机、不含凭据的后端来源，保留浏览器原始 Origin，由后端继续验证。
- 经用户确认，本轮真实验收复用此前隔离联调库：Web 为 `localhost:3000`，进程环境的 `VITE_API_PROXY_TARGET` 指向 `http://127.0.0.1:18080`。现有 `8080` 服务和另一套数据库保持原状态；Backend 启动程序与源码未修改。
- Cookie 由浏览器和服务端管理，前端不读取 HttpOnly Cookie、不保存 Token/角色/密码。重新打开页面通过 `/auth/me` 获取当前身份，管理路由重新校验服务端角色。
- 写请求先获取 `/auth/csrf`，令牌只在内存中保留。登录更换会话后重新获取；CSRF 失效不自动重放写请求。
- 登录使用 `account/password`；注册仅使用 `email/password/verificationCode`。客户端角色、昵称、邀请码不参与注册授权。
- 响应必须是 `code: "OK"` 的统一结构。401 清除页面身份，403/429/503 保留服务端错误；错误对象不包含原始请求和凭据。
- 不启用旧 Mock 后端或本地身份回退。旧版凭据会清理；切换账号后的迟到响应不能覆盖当前页面身份。

## 功能分支与验收

以当前 `develop` 为集成分支，每个功能单独开发，提交使用 `feat: 中文描述` 等格式。已实现认证、目录详情、点评与图片/菜品/档口投稿、个人记录、内容审核与目录管理、用户管理。复用功能分支时先将其指向最新已集成 develop，再修改并合入；本轮按照负责人明确授权直接推送 develop 和对应功能分支。

每个功能提交前运行 `npm run check`。单元替身只用于验证前端行为，不能作为已与 Backend 联调的证据；真实接口和页面验收结果在完成对应功能后记录。

## 目录与详情

食堂列表来自 `/dining-halls`，食堂详情在该真实列表定位；档口与菜品分别来自 `/dining-halls/{id}/stalls` 和 `/stalls/{id}/dishes`。URL 保留食堂、档口、菜品三级上下文，详情和图册重新校验真实父级。评分读取 `/dishes/{id}/rating` 的每日物化快照，不从页面评论计算。

评论与图册读取各自的分页接口，展示用户 ID、正文、评分与批准图片。金额固定两位小数，零价格正常显示；空图显示明确缺省文案。存储引用只进入同站媒体路径，旧 HTTPS 图片以匿名、无引用来源的请求加载；拒绝可执行图片地址或其他本机服务地址。页面卸载或请求更新后丢弃迟到结果，账号变化后重新创建页面。

2026-10-15：目录分支完整质量门禁通过（134 项单元测试、Lint、格式检查、构建）。隔离联调环境中，真实浏览器已验证 Cookie 登录、食堂→档口→菜品→图册、空评分/空图及刷新后的服务端会话恢复。后端源码没有修改。

## 点评投稿

点评只从菜品详情的“写点评”按钮进入该菜品的 `/reviews/new` 子页面，桌面和移动导航不再提供独立点评入口。表单使用菜品详情响应直接显示实际菜品、食堂和档口名称，校验网址的完整父级关系；不显示重新选目标的控件，也不使用查询参数更改目标。`POST /dishes/{id}/reviews` 仅提交 `rating/content`，身份和 pending 状态由后端确定。提交中固定目标，失败保留正文；成功返回原菜品详情，取消和面包屑保留完整所属参数。评分校验为整数 1–5，正文按后端 TEXT 规则处理，不另加 220 字上限。

该功能完整门禁通过（142 项单元测试）。真实浏览器已通过 Cookie/CSRF 提交带 HTML 字符的测试正文，收到待审核成功提示，菜品公开评论仍为空，没有把 pending 内容当作已发布。

## 个人记录

个人身份读取 `/users/me/profile`，评论和四种投稿记录分别读取当前用户的真实分页接口；不提交用户 ID，也不生成不存在的审核时间。删除本人评论只在服务端成功后刷新列表，失败保留原记录。修改密码仅发送 `oldPassword/newPassword`，成功后要求重新登录，失败保留输入与身份。

该功能完整门禁通过（146 项单元测试）。真实浏览器确认个人身份、此前投稿历史、本轮 pending 点评及原样显示的 HTML 字符；改密的失败和成功处理通过单元测试验证。

## 图片、菜品与档口投稿

图片先通过 multipart `/uploads/images` 上传，再使用服务端返回的本人媒体引用投稿。菜品仅发送名称、简介、可空参考价格与图片引用；档口只发送名称、简介与封面引用，不含 floor。投稿目标重新校验真实父级关系，成功后展示等待审核，不直接插入公共目录。上传与投稿失败保留当前草稿和引用，重复点击不会并发写入；页面离开后释放本地预览。

完整检查已通过。真实浏览器已上传本地非个人 PNG 测试图片并提交，个人图片记录显示 pending，审核原因和历史时间来自后端。

## 内容审核与日志

审核队列统一使用 `/admin/moderation`，只查询 pending/approved/rejected；四类对象按实际 type 提交 approve/reject，审核人由后端确定。驳回原因必填，菜品通过前补齐合法价格，409 冲突保留原内容和输入。审核日志来自 `/admin/moderation/logs`，只展示真实 approve/reject 记录。

真实浏览器已由管理员通过本轮点评及图片，并在日志中查到对应投稿 ID、审核人、时间和说明。菜品详情随后显示批准图片和点评正文，HTML 字符按文本显示；评分仍读取每日快照，没有即时伪算。

## 目录与正式评论管理

管理目录使用 `/admin/catalog/dining-halls|stalls|dishes` 的分页与详情接口；创建从真实分页父级选择，编辑保持原归属。只发送该类型适用的名称、简介、价格、封面、状态和排序字段；菜品封面只是批准图片的查询结果，不作为菜品字段写入。封面更换走本人上传，已有未变封面可保留。删除失败保留记录并展示后端 RESTRICT 冲突，可改为停用。正式评论列表来自 `/admin/reviews`，删除必须填写 reason，不生成设计以外日志动作。

真实浏览器已创建一条独立停用食堂记录，详情回读后修改排序并确认列表返回新值。字段过滤、零价格、归属保持和删除冲突由单元测试验证。

## 用户管理

仅平台管理员展示用户管理入口，调用 `/admin/users?q=&page=&size=` 与 `PUT /admin/users/{id}`。更新只发送 role/status，使用 user/admin/superadmin 与 active/disabled 的实际取值。自身权限禁止编辑，取消不请求，失败保留输入和原记录。邀请码、他人密码重置、虚构看板和用户操作数据库日志入口已移除；旧看板地址跳转到真实用户管理。

真实浏览器已验证平台管理员身份、三个样例用户的实际字段、自身编辑禁用、按邮箱搜索及正式评论计数。字段过滤、取消、权限失效和错误枚举处理由单元测试覆盖。
